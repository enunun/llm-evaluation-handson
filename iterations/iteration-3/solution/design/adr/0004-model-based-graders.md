# 0004 自由記述はコードの採点器で測れる観点をコードで測り，残りをLLM Judgeと意思決定モデルで測る

## 状況

返信の下書きは自由記述であり，正解の文字列と比べる採点はできない．
返信の品質には，方針にない約束をしていないか(QC02-2)，丁寧な言葉遣いの指示に従っているか(QC01-4)，問い合わせに答えているか(QC01-1)という複数の観点がある．
LLM Judgeは柔軟だが，それ自体が非決定的であり，形式を守らない応答を返すことがある．
意思決定モデル(Ollamaの`/v1/systemone`で動くTev1)は，文章を生成せず，型付きの質問に確率で答える．

## 決定

- 1つの採点器は1つの観点だけを測り，品質特性を1つ割り当てる．
- 文字列で判定できる観点はコードの採点器(promptfooの`not-icontains`)で測る．
- 丁寧さは，ルーブリックを渡したLLM Judgeで測る．Judgeには，理由を先に書かせ，`pass`，`fail`，`unknown`のどれかをJSONで答えさせる．
- 問い合わせに答えているかは，意思決定モデルの`noul`型の質問で測り，確率がしきい値(既定0.5)以上なら合格とする．
- 採点の結果を`pass`，`fail`，`unknown`(採点器が判断できない)，`error`(採点できない)の4つにする．`unknown`と`error`は合格率の計算から除き，件数を報告する．
- 自作のアサーションは採点の結果をメタデータの`outcome`に残し，`evalstats`はそれを読む．
- 偽のJudgeと偽の意思決定モデルも，シード，入力，試行の番号から決まる乱数で揺らす．試行の番号は，プロバイダがメタデータの`trial`に記録する．

## 理由

- コードの採点器は速く，安く，揺れない．Anthropicの"Demystifying evals for AI agents"は，決定的な採点器を使えるところでは使い，モデルの採点器は必要なところに限ることを勧めている．
- 1つのJudgeが複数の観点を採点すると，どの観点で落ちたのかが分からず，観点どうしの判断が混ざる．観点ごとに別のJudgeを用意する．
- 判断できないときの逃げ道(`unknown`)がないと，Judgeは情報が足りなくてもどちらかに決めてしまう．`unknown`を不合格と区別して数えると，Judgeが判断に困った件数が見える．
- 理由を先に書かせると，判定がその理由に沿いやすくなり，トランスクリプトを読むときに判定の根拠を確かめられる．
- `error`を不合格に数えると，Judgeの不調が製品の品質の低下に見える．採点の失敗は製品の失敗と分けて報告する．
- 意思決定モデルは確率を返すため，しきい値を変えて合格の厳しさを調整できる．文章を生成しないため，形式の誤りによる`error`が起きにくい．

## 影響

- モデルの採点器の判定が正しいかは，まだ確かめていない．Iteration 4で人手ラベルと照らし合わせて検証する．
- Tev1は英語以外で十分に試験されていないため，質問は英語で書き，状態は日本語のまま渡す．日本語の返信に使えるかは，Iteration 4の検証で確かめる．
- 全タスクの合格率が1.0の採点器では，標準誤差が0になり，区間が`[1.00, 1.00]`に潰れる．タスクごとの区間を合わせて読む必要がある．
- 評価の時間は，Judgeと意思決定モデルの呼び出しの分だけ増える．
