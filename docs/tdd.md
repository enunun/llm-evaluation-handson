# テスト駆動開発の進め方

このコースのコードは，すべてテスト駆動で書く．
評価の対象であるLLMは非決定的だが，評価のための仕組み(製品の後処理，プロバイダ，採点器，集計，統計)は決定的なコードであり，テストで確かめられる．

## Red → Green → Refactor

1. Red：これから作る振る舞いを1つ選び，その振る舞いを確かめるテストを書く．テストを実行し，期待どおりの理由で失敗することを確かめる．
2. Green：テストを通す最小のコードを書く．決め打ちの値を返す仮実装でもよい．次のテストが，仮実装を一般的な実装へ押し出す．
3. Refactor：テストが通ったまま，重複を除き，名前を整え，関数を切り出す．

失敗を確かめずに書いたテストは，何も確かめていないことがある．Redを飛ばさない．

## テストリスト

実装を始める前に，確かめるべき振る舞いを`TESTLIST.md`に書き出す．

- 要求と使用例を読み，「〜なら〜する」の形で1項目1振る舞いを書く．
- 単体テストと統合テストに分ける．
- 簡単な項目から並べる．仮実装で通る項目を先に，一般化を迫る項目を後に置く．
- 境界と異常を忘れない(空の入力，形の違うデータ，外部の失敗)．
- 実装中に思いついた振る舞いは，すぐに書かずにリストへ足す．
- 既存の振る舞いを変えるIterationでは，期待値が変わる既存のテストを「〜を〜に変える」の形で書く．
- 通した項目には`[x]`を付ける．

## 単体テストと統合テスト

| | 単体テスト | 統合テスト |
| --- | --- | --- |
| 置き場所 | `test/unit/<モジュール名>.test.ts` | `test/integration/` |
| 確かめること | 1つのモジュールの関数を単独で | promptfooで実際にスイートを評価し，その結果JSONを`evalstats`の`main`に渡した組み合わせ |
| LLM | 決めた応答を返す偽物を注入する | シード付きの偽LLM |

1つのモジュールに1つのテストファイルを置き，モジュールが存在する限り使い続ける．
Iterationで機能が変わったら，そのファイルにテストを足すか，期待値を書き換える．
テストファイルの名前にIterationの番号は付けない．

## 非決定的なものをテストしない

本物のLLMを呼ぶテストは，同じコードでも通ったり落ちたりする．
LLMの品質は評価で測るものであり，テストで確かめるものではない．
テストでは，LLMをポートの背後に置き，偽物を注入する．
乱数を使うコードは，シードを固定して決定的にしてから確かめる．

## テストの実行

パッケージのディレクトリで実行する．

| 操作 | コマンド |
| --- | --- |
| すべてのテスト | `pnpm test` |
| 単体テストだけ | `pnpm test:unit` |
| 統合テストだけ | `pnpm test:integration` |
| 1つのテストファイル | `pnpm vitest run test/unit/<名前>.test.ts` |
| 保存のたびに実行 | `pnpm vitest --project unit` |
| 型検査 | `pnpm typecheck` |

リポジトリ全体の検証は，ルートで`mise run check`を実行する．
